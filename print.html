VardUI

VardUI documentation

VardUI is a cross-platform UI framework whose primary “developer” is an LLM agent: the Vard language, a fine-grained reactive runtime, a headless platform simulator, tooling with machine-applicable fixes, and a package system designed for a world where a model adds dependencies and a person approves them.

These pages are for people. The references for agents are compiled into the vard binary and printed by vard doc (sources in knowledge/).

Getting started

Install

Prebuilt binaries for Linux, macOS and Windows are on GitHub Releases. The install scripts download the latest one, verify its SHA-256 and put it into ~/.vard/bin:

curl -fsSL https://raw.githubusercontent.com/vardemin/vardui/master/install.sh | sh

irm https://raw.githubusercontent.com/vardemin/vardui/master/install.ps1 | iex

From source (Rust 1.98, pinned in rust-toolchain.toml; rustup fetches it automatically):

git clone https://github.com/vardemin/vardui.git
cd vardui
cargo build --release

The binary is vard (target/release/vard from source). Everything a person or an agent needs — compiler, headless runtime, test runner, reference, package manager, registry server and MCP server — is in this one file.

First project

vard new hello

hello/
  app.vard              the root view App
  vard.toml             manifest: app name, dependencies, policy
  tests/smoke.vtest     a scripted test
  AGENTS.md, CLAUDE.md  instructions for agents (the package list block updates itself)
  .mcp.json             the `vard mcp` server for Claude Code and other clients
  .claude/skills/       skills vard-app, vard-debug, vard-native, vard-design, vard-packages

app.vard:

view App {
  state count = 0

  Column(padding: 24, gap: 16, justify: .center, align: .center, grow: 1) {
    Text("Hello, Vard", style: .title)
    Text("Tapped {count} times", color: .muted)
    Button("Tap me", onTap: { count += 1 })
  }
}

The development loop

The same for a person and for an agent; every step takes milliseconds and is deterministic.

cd hello
vard check --fix          # types + machine fixes
vard run                  # the screen as text (semantic tree)
vard run --do 'tap "Tap me"; expect "Tapped 1 times"'
vard test                 # every tests/*.vtest

vard run prints the screen as a tree with ids:

> tree
screen 390x844 light
App @1
  Text "Hello, Vard" @2
  Text "Tapped 0 times" @3
  Button "Tap me" @4

A mutating action prints only what changed:

> tap "Tap me"
~ Text "Tapped 1 times" @3

A compile error is a location, the line of code and a fix:

app.vard:2:3 error E0201: unknown element `VStack`
  2 | VStack(gap: 8) {
  fix: `VStack` -> `Column` (auto: vard check --fix)

Add a package

vard search tailwind
vard add tailwind
vard doc tailwind          # the package's AGENT.md + the API generated by the compiler

After vard add the package’s public names are visible without imports: TwButton("Save", onTap: save). More in Using packages.

Run on Android

cd platforms/android
./gradlew installDebug -Pvard.app=examples/todo

You need the Android SDK/NDK and cargo-ndk — see Android shell. The build bundles the app and its packages (vard bundle) and includes the packages’ native modules by itself.

Working with AI agents

VardUI was designed around one question: what does each step of the “write → check → run → understand what went wrong” loop cost an agent — in tokens, in time, and in the probability of a mistake. Below is what the answer is made of and how to use it.

Principles

PrincipleHow it is implemented
Write it right the first timea small regular language, syntax close to Swift/Kotlin/TS, one form for each thing
Fix without thinkingevery diagnostic is file:line, the line of code, fix:; vard check --fix applies fixes to a fixed point; “habit” tables (VStack → Column, onPress → onTap, "a" + n → "a{n}")
See without visiona semantic tree ≈ 100 tokens; actions print diffs; why explains sizes; lints describe the recipe
Knowledge from one sourcethe reference is compiled into the binary and generated from the element registry — it cannot drift from the compiler
Determinismheadless runtime, bundled font, platform simulator, MVS for versions: same inputs, same result
A person decides outward-facing and risky stepsapproving package capabilities and publishing are not available through MCP

What an agent gets in a project

vard new creates:

  • AGENTS.md (and CLAUDE.md → @AGENTS.md) — the work loop, debugging rules, conventions, and a <!-- vard:packages --> block that the package manager keeps current;
  • .claude/skills/ — vard-app (screen patterns), vard-debug, vard-native, vard-design, vard-packages; packages’ skills are added on install as <package>-<skill>;
  • .mcp.json — the vard mcp server.

Recommended agent loop

  1. Once per session — vard doc (or vard_doc).
  2. Edit .vard → vard check --fix → fix the rest.
  3. vard run --do "…" — the screen and actions; why for sizes, state/log for values.
  4. A test for every feature and bug: tests/*.vtest, vard test.
  5. Need “library” functionality — vard search → vard info → vard add → vard doc NAME. Never guess names; on P008, ask the user.
  6. A screenshot — only to judge how it looks.

Why packages are built this way

The package system continues the same principles (overview):

  • the compiler computes the contract — an agent does not need to trust a description or read code to know a package’s API and capabilities;
  • installation never guesses — protection against hallucinated names;
  • knowledge has a budget — AGENT.md ≤ 6 KB, the API is generated;
  • updates are mechanical — package migrations become fix:es;
  • a package runs headless — [sim] and tests at publish time;
  • risk stays with a person — sensitive capabilities are approved in vard.toml.

The Vard language

Vard is a declarative, statically typed language for user interfaces. Its syntax is close to Swift/Kotlin/TypeScript (where models have strong priors), but there is one way to write each thing: no modifier chains, no decorator annotations, no alternative syntaxes. The full reference for agents is vard doc (≈ 3k tokens); this page says the same in more detail, with the reasons.

Files and projects

  • Sources are *.vard. All files of the project directory (recursively, except hidden directories, target, build, node_modules) form one namespace: there are no imports.
  • The app’s root view is view App. Without it, vard run mounts the last view declared in the project’s code.
  • Dependencies are declared in vard.toml; their public names are visible without imports (rules: Using packages).
  • Statements end at the line break; ; is error E0106 with an auto-fix. Line breaks are allowed inside (/[ and before continuation lines (starting with .x, &&, ||, ?, :).

Top-level declarations

struct Todo { id: Int, title: String, done: Bool = false }   // fields `name: Type [= default]`
enum Filter { all, active, done }                            // values: .all .active .done
const maxItems = 50
fn total(xs: [Int]) -> Int { return xs.sum() }               // no `-> T` = returns nothing
extern fn share(text: String) -> Bool                        // a platform call
extern fn load(id: Int, done: fn(Item?, String?))            // an async call: callback
extern event orderUpdated(order: Order)                      // a platform event
theme { brand: #7C3AED, primary: #7C3AED, font: "Inter" }   // color tokens and the default font
theme dark { brand: #C4B5FD }                                // dark-mode values
view Name(params) { members }

Declaration order does not matter: types and functions can refer to each other in any order. Keywords from other languages (func, function, component, class, interface…) are recognized and fixed to the Vard equivalent (E0110, with fix:).

Views

view Card(title: String, onTap: fn() = {}, bind value: Bool, content: slot) {
  state count = 0                      // reactive mutable state (the initializer runs once)
  state items: [Todo] = []
  pref darkMode = false                // state kept by the platform; app-wide by name
  let doubled = count * 2              // derived value, recomputes itself, read-only
  fn inc() { count += 1 }              // can read and write state
  on appear { load() }                 // event handler while the view is on screen
  on back if count > 0 { count -= 1 }  // `if` = active only while the condition holds
  Column(gap: 8) {                     // then exactly one UI tree
    Text(title)
    content                            // a bare lowercase name inserts the slot parameter
  }
}

Order inside a view: members first (state, pref, let, fn, on), then elements. A view body is declarative: there are no statements in the tree (E0113); logic lives in fn members and handlers.

Parameters

FormMeaning
name: Type [= default]read-only; reactive — updates when the caller’s value changes
bind name: Typetwo-way: the caller passes a mutable place (Checkbox(value: todo.done))
name: slota child block: Card { Text("Hi") }; at most one slot per view

The first argument (the first non-slot parameter) may be positional; the rest are always name: value (E0207). Every view use also accepts “outer” props applied to its root: width height minWidth minHeight maxWidth maxHeight aspectRatio grow alignSelf id opacity offsetX offsetY scale.

State: state, pref, let

  • state — a signal. Changing it re-runs exactly the props that read it.
  • pref — the same as state, but the value is kept in platform preferences (SharedPreferences, UserDefaults, headless — the simulator’s memory) under the key vard.pref.<name> and restored at launch. Any data type (structs, lists, maps). All prefs with one name are one app-wide value, and their types must match (E0223).
  • let — a computed value (lazy, cached, dependencies tracked automatically).

The UI tree

Element(args) { children }      // braces only for elements that take children
if cond { ... } else if c2 { ... } else { ... }
for t in todos by t.id { ... }      // `by` = a stable unique key
for t, i in todos by t.id { ... }   // i = index (Int)
for i in range(0, 5) { ... }

by is effectively required for structs with an id (W0401 without it): the key keeps a row’s identity across sorting and filtering. Two equal keys are R0002.

Elements are not values: they cannot be stored in a variable or returned from a function (E0212); compose with views and slot parameters.

Expressions

+ - * / %   == != < <= > >=   && || !   cond ? a : b   a ?? fallback   x! (unwrap)
list[i]   map["k"] (T?)   s.field   .name (an enum variant or a color token)
x => x.done   (a, b) => a + b   x => { stmts }   { stmts }   // lambdas

.name is resolved from the expected type: an argument, a variable’s annotation, or the other side of == (x == .all). Lambda parameter types come from where the lambda is passed — no annotations needed.

Not in Vard: self/this, ?. (E0121), ++/-- (E0115), ===, semicolons, imports, classes, modifier chains (E0119), @State (E0124), { x -> } (E0126). Each of these habits is recognized and comes with a fix.

Statements (function and handler bodies)

let x = 1          var y = 2          x = v   x += v   x -= v
map["k"] = v       map["k"] = nil     // removes the key
if c { } else { }  for x in list { }  return v   print(a, b)

Built-in functions: range(a, b) (a to b-1), min, max, print (to the log: vard run --do log).

What is mutable

state, pref, bind parameters, local vars, fields and elements of those (todos[i].done = true, profile.name = "x", counts["a"] = 1) and the loop variable of a for that runs directly over state (for t in todos by t.id { Checkbox(value: t.done) }).

Parameters, let and items of a computed list (for t in todos.filter(...)) are read-only (E0401); such state is changed by key: todos.removeWhere(x => x.id == t.id).

Values are copied, never shared (copy-on-write inside the runtime): a function that receives a struct received a copy. The model never has to think about aliasing.

Themes and tokens

Colors in views are set through tokens only — then dark mode just works: .background .surface .text .muted .primary .onPrimary .border .danger .success .warning .clear. Custom tokens are declared in theme { } (light values) and theme dark { }. font: "Inter" in a theme sets the default family (font files go into the project’s fonts/). Details: UI.

Localized text

strings { hello: "Hello, {name}", items: "{n} items" }      // the default table: the source language
strings ru { hello: "Привет, {name}", items: "{n} шт." }    // a translation
view Greeting(name: String, n: Int) {
  Column {
    Text(t("hello", ["name": name]))
    Text(t("items", ["n": "{n}"]))
  }
}
  • t(key, [placeholder: value]) returns the text for the current locale (a reactive global, e.g. "ru", "pt-BR"): the exact language table, else its base language (pt-BR → pt), else the default table. Changing the locale re-renders exactly the texts that use t().
  • The compiler checks literal keys against the default table (E0240, with a fix for typos), placeholders against the default text (E0241), and reports missing translations (W0405). Placeholders are names ({n}), not expressions (E0242) — compute values in code.
  • The host sets the locale from the system (Android: the configuration’s first locale, also on change); in tests: the locale ru action.

The platform boundary

extern fn is a call into the platform, extern event is an event from the platform with a handler on name(params) [if cond] { }. Only data crosses the boundary (Int Float String Bool Color, structs, enums, lists, maps, optionals) and callbacks fn(T) for results that arrive later (E0317). Details: Platform.

Qualified names

A name from a package can be qualified with the package name: charts.BarChart(...), state s: ui.Style, geo.distance(a, b), and a std one with std.Button. This is needed only when two packages conflict (E0231); otherwise names are written as they are. Names starting with _ are private to their package.

Layout

The model is CSS flex semantics in a single pass: constraints go down, sizes go up.

  • align — the cross axis: .start .center .end .stretch (default .stretch).
  • justify — the main axis: .start (default) .center .end .between .around .evenly.
  • grow — a share of the free space on the main axis; alignSelf overrides align for a child.
  • Sizes: width height minWidth minHeight maxWidth maxHeight aspectRatio.
  • Spacing: padding paddingX paddingY paddingTop paddingBottom paddingLeft paddingRight; safeArea: .top|.bottom|.all|.vertical|.horizontal adds the system insets to padding.

Every node remembers why it got its size on each axis. vard run --do 'why @2' prints the chain of rules up to the root — the main tool for “why doesn’t it fit”:

Reactivity and execution model

The decision and its alternatives: ADR-0002. This page explains how it works and what rules follow for code.

The graph

In codeIn the runtime
state x, pref xSignal — a cell with a list of subscribers
let y = ..., view parametersComputed — a lazy cached value; dependencies are collected on read
every dynamic propEffect — writes one field of one node
if / for in the treea structural Effect over a fragment of the tree
a viewScope — owns everything created inside it

A view body runs once, at mount. After that, changing a state wakes exactly the effects that read it: count += 1 rewrites the text of one Text and rebuilds nothing. No virtual DOM, no component re-rendering, no manual memoization.

Equality cut-offs

At every level: a signal does not notify for the same value; a prop does not touch the node for the same value; unchanged props do not mark layout dirty. Static props (literals, enum values, lambdas) create no effects at all.

Lists

for t in todos by t.id reconciles rows by key. Each row has its own value signal, so changing one item of a 3000-item list re-runs the effects of one row (measured in the repository: 7 actions over 3000 rows — 35 effect runs). Without by, rows are matched by position: a reorder turns into changes in every row.

Order and consistency

Effects run in creation order (parent before child), so there are no intermediate inconsistent states (“glitches”). Disposing a scope (a view left the screen, an if branch switched) frees all of its effects, nodes, signals and event handlers.

Rules for code

  1. Rendering is pure. Writing state while computing a prop, a let or an if/for condition is R0003. Writes go into handlers (onTap, onChange, onSubmit, on event) and functions called from them.
  2. A let does not read itself (R0004), directly or through other lets.
  3. Values are copied. let t = todos[0]; t.title = "x" does not change the list; change the place: todos[0].title = "x".
  4. Keys are unique. R0002 — two equal by keys.

Runtime errors do not crash the app: the problem becomes an R diagnostic with file:line, the value becomes nil.

Measuring

vard run --do 'tap "Add"; stats' prints effect runs, layouts and node count — enough to see wasted work without a profiler.

Platform and native modules

Everything platform-specific goes through two declarations — they are also the boundary between Vard and native code:

  • extern fn name(params) -> T — the app calls the platform;
  • extern event name(params) — the platform tells the app; the handler in a view, on name(params) [if cond] { ... }, is active while the view is on screen.

The standard platform is declared in Vard itself (vard doc std); every function is implemented by the headless simulator, the Android host and the Apple host (iOS/macOS). The reference for agents is vard doc native.

Lifecycle and system

on appear { load() }                  // this view instance was just shown
on appResume { refresh() }    on appPause { save() }
on deepLink(url) { route(url) }       // vard://...

Globals (reactive, read-only): safeArea (top bottom left right), keyboardHeight, backProgress, isDark, screenWidth, screenHeight, platform. Functions: setColorScheme(.dark|.light|.system), openUrl(url), shareText(text), haptic(.success), openAppSettings().

Back and predictive back

on back if stack.count > 1 { stack.removeAt(stack.count - 1) }
Column(offsetX: backProgress * 64, opacity: 1 - backProgress * 0.3) { ... }

The innermost enabled handler takes the gesture. With none enabled, the system handles back (on Android 14+ with the system back-to-home animation). Whether the app intercepts back is passed to the host in every frame.

Edge-to-edge

The root always draws under the system bars. If the code never mentions safeArea, the runtime pads the root itself. Otherwise you control placement: safeArea: .top on an element adds the insets to its padding, safeArea.bottom reads the value (including the keyboard). The focused input scrolls above the keyboard automatically.

Storage

pref onboarded = false            // settings, app-wide by name
let t = secureGet("token")        // String? — Keychain / Android Keystore (AES-256-GCM)
secureSet("token", value)         // -> Bool;  secureRemove("token")
prefGet(key) / prefSet(key, v) / prefRemove(key)   // raw string preferences

Permissions

state cam: PermissionStatus = .notDetermined

    struct Place { name: String, lat: Float, lng: Float }

extern event locationChanged(lat: Float, lng: Float)
  2. Build the UI and test it headless (mock, resolve, emit — see Testing).
  3. Generate typed Kotlin: vard bindings --kotlin --class PlacesModule --out ... and implement the abstract methods (callbacks may be answered from any thread; send() instead of resolve() for listeners).
  4. Register it: MainActivity.modules(), dev.vard.module.<name> meta-data in a library’s manifest — or, better, ship it as a package with [native.android]: then any app gets it with one vard add, and the Android shell includes the module by itself (Writing a package).

How data crosses

The format is JSON. Encoding is untyped; decoding follows the type declared in Vard (struct fields by name, enums by variant name, defaults for missing fields). So one native function serves any app type: firestoreGet* from the firebase package returns a document, and Vard turns it into your struct.

Functions in arguments become {"$callback": id}; the host answers with callback(id, json, keep). A callback of a view that has left the screen is dropped silently. A function not implemented on the device is R0010.

extern fn/extern event names are global to the app: the platform calls them by name. Two packages cannot declare the same native name (E0233).

Package system overview

The problem

In today’s ecosystems (npm, Cargo, Go modules, SwiftPM, pub.dev) a package is an archive of code plus what its author claims about it: a version, a description, dependencies. Everything else — what the package can do, what breaks on upgrade, whether to trust it — a person finds out by reading code, changelogs and issues.

In VardUI, dependencies are mostly added by an LLM agent. For an agent the usual model has three systemic defects:

  1. Hallucinated names. Models confidently “remember” packages that do not exist, and attackers register those names (“slopsquatting”). Installing by a guessed name is a classic attack path.
  2. Claims instead of facts. Semver is an honor system; changelogs are written for people; what a package does with the device is written down nowhere. An agent cannot check any of it more cheaply than by reading all of the code.
  3. Expensive knowledge. To start using a package an agent reads a README of thousands of tokens, and after an upgrade it guesses what was renamed.

The solution: package = code + contract + knowledge + proof

PartWhat it isWho produces it
Code.vard sources, optionally a native module and resourcesthe author
Contractthe public API and capabilitiesthe compiler — computed from code, not declared
KnowledgeAGENT.md ≤ 6 KB (≈ 1500 tokens) + the generated API + skillsthe author + the compiler
Proofheadless tests of example/ and the package, run by the registry at publishthe registry
Migrationsrenames that become fix:es for consumersthe author
Simulation[sim] answers for the package’s externs in headless modethe author

This gives properties classic package managers do not have:

  • Semver is enforced. The compiler compares the new version’s API with the previous one: removing or changing something is major, adding is minor, anything else is a patch. The registry will not accept 1.0.1 with a broken API (P015) and suggests the minimal acceptable version.
  • Capabilities are facts, not promises. The compiler sees the code call secureGet, declare an extern fn, subscribe to pushReceived or load https://. The manifest must match what was computed (P013); the consumer must approve sensitive capabilities in [policy] (P008); vard.lock records them, so a new capability in a dependency is a line in a code-review diff.
  • Upgrades are mechanical. vard update prints the API diff, and vard check --fix applies the package’s migrations to the app’s code (E0234). The agent does not read a changelog.
  • Installation never guesses. vard add installs exact names only; a typo gets “did you mean” from the real index (P001). The registry refuses a name one edit away from an existing name of another owner (P010).
  • Knowledge is cheap and bounded. vard doc shows the project’s packages one line each; vard doc NAME shows AGENT.md and the generated API. The document budget is checked at publish (P011). The package block in the project’s AGENTS.md is updated on install, so an agent sees the dependencies without a single tool call.
  • A package is verifiable without a device. Tests run headless at publish; [sim] gives consumers a working vard run right after vard add, even for packages with native code.

Namespaces without imports

The language deliberately has no imports (ADR-0001): one form of writing, no line where a model can get a path wrong. Packages keep that:

  1. an unqualified name is looked up in its own package (the app is a package too), then in direct dependencies, then in std;
  2. your own declarations always win over packages;
  3. if two direct dependencies export a name — E0231, write pkg.Name;
  4. transitive dependencies are invisible (E0232), _ names are private (E0230);
  5. extern fn/event names are global — the platform calls them (E0233).

The result: adding or upgrading one package cannot change the meaning of anyone else’s code. The compiler renames conflicting declarations to pkg.Name before type checking, so the runtime and inspection know nothing about packages. Details: Using packages; implementation: crates/vard-lang/src/link.rs.

Version resolution: minimal version selection

A requirement is a minimum on a compatibility line ("1.4" = ≥ 1.4.0, < 2.0.0). For each package the largest of the minimums anyone requires is selected (ADR-0006). No SAT solver, no “latest”: the result depends only on the manifests — today, tomorrow and in CI. The lockfile decides nothing; it pins hashes and records capabilities. One version of a package per app (a shared namespace); incompatible lines are P006.

Hosting: static, content-addressed, signed

A registry is a set of static files (ADR-0007): config.json, catalog.json, index/NAME.json, blobs/SHA256.vpk, and a signed log log.txt + log.head. Any CDN, bucket, GitHub Pages or directory can serve it; vard registry serve adds a publish API. A client pins the registry key on first contact, verifies the signature and the log’s hash chain, and then the hash of every archive. Trust does not depend on the host: a mirror can delay an update but cannot substitute what was published. Details: Registries and hosting; threats: Security model.

Delivery to devices

vard bundle collects everything a device executes: the app’s and packages’ sources (@name/...), vard.lock, resources, and bundle.json with a hash and a native fingerprint — the list of externs and native modules. The Android shell runs vard bundle during the build and includes the packages’ native modules automatically. The fingerprint is the compatibility key for over-the-air updates: an interpreted bundle can be delivered without rebuilding the APK as long as the native part did not change. Details: Delivery to devices.

The manifest can be edited by hand: any vard command (check, run, test, doc) notices that vard.lock is stale and reinstalls, saying so in one line.

Registries are looked up in order: the project’s [registries] → ~/.vard/config.toml → the public registry vard (vardemin/vard-registry, served at https://vardemin.github.io/vard-registry) → builtin (the packages bundled with the toolchain, available offline). The default registry is vard unless default (or the VARD_REGISTRY variable) says otherwise; VARD_OFFLINE=1 removes the public registry and makes builtin the default. Each dependency comes from exactly one registry — its own registry = ... or the default — never “wherever it was found”: this rules out dependency confusion attacks.

Git dependencies

{ git = URL, tag | rev | branch = "...", dir = "sub/dir" } takes a package straight from a repository — any URL git understands, or a local path relative to vard.toml. The commit the reference resolves to is pinned in vard.lock together with the content hash of the package files, so a branch does not move under the project until vard update NAME re-resolves it:

$ vard update charts
~ charts 1.0.0 -> 1.1.0 (git 3f2a9c1e0b7d -> 8c41d0a2e9f3)

Git packages go through the same capability policy as registry packages. A package that depends on a git (or path) package cannot be published to a registry (P021): registries only reference registry versions.

New packages are quarantined

A package from a remote registry whose first version was published less than 72 hours ago is not installed without --allow-new (P024). Fresh packages are where look-alikes and typosquats live, so a person confirms them after a look at vard info NAME (owner, publication time, provenance — which CI run built the archive). vard search and the registry’s web page mark such packages NEW. The MCP tool vard_add has no --allow-new: an agent asks the user. Directory registries (your own) are not quarantined.

Packages in headless mode

A package’s externs answer with values from its [sim] (for example, authCurrentUser → nil); the rest stay pending until a test says resolve/send. mock in a test overrides [sim]. That is why vard run works right after vard add — even for a package wrapping a native SDK.

Package files are shown as @name/file.vard:LINE. Packages’ warnings are not printed (that is the author’s business); errors are. vard check --fix never writes into package files: they are inputs from the cache (~/.vard/cache/pkgs/).

Public API

Public is everything declared at the top level that does not start with _: views, structs, enums, functions, extern fn/event, constants, theme tokens. See what consumers see:

vard api charts/            # API + capabilities with evidence

view BarChart(values: [Int], max: Int = 100)
view Badge(label: String)
capabilities: none

Recommendations:

  • Helpers start with _: view _Bar(...), fn _scale(...). They can change without a major version.
  • Exported names should be distinctive: they live in the app’s namespace. A conflict with another package will not silently break the build (E0231), but it forces consumers to qualify.
  • Parameters with defaults — adding one stays a minor change.
  • A package’s theme tokens (theme { }) become the app’s tokens: that is how design systems are shipped (this is how tailwind works).

AGENT.md

What an agent reads to use the package (vard doc charts = AGENT.md + the generated API + capabilities). The budget is 6 KB ≈ 1500 tokens (P011). Write for a model:

  1. one sentence — what it is and when to use it;
  2. the main views/functions — one compiling example each;
  3. non-obvious rules (what goes into a bind, which tokens to use);
  4. how to test headless: what [sim] answers, what needs resolve/emit.

Do not repeat the API list — it is generated and always accurate.

The example as proof

example/ is an ordinary app that depends on the package by path. The publish gate compiles it and runs every .vtest (a test runs against the nearest vard.toml). It is both “how to use it” documentation and a check that the package works with the current core.

vard test charts/           # the package's and example/'s tests

Capabilities

The compiler computes capabilities from the code: calls to secureGet/secureSet → secure, requestPermission → permissions, getPushToken, showNotification, on pushReceived → push, pref and prefGet → prefs, openUrl → links, shareText → share, on deepLink → deeplinks, https:// strings → network, declaring extern fn/event → native. The manifest’s capabilities must match (P013, with a ready replacement line). Extra capabilities are a warning: consumers would have to approve something unneeded.

Native code

A package can ship the implementation of its extern fn/event:

  1. declare the API in Vard in the package’s sources;
  2. generate a base class: vard bindings charts/ --kotlin --package dev.example.charts --class ChartsModuleBase;
  3. put an Android library into native/android/ (build.gradle.kts, an AndroidManifest.xml with <meta-data android:name="dev.vard.module.charts" android:value="dev.example.charts.ChartsModule"/>, the Kotlin implementation);
  4. add [native.android] to the manifest;
  5. set [sim] so consumers can run the app headless.

The Android shell includes the module automatically: settings.gradle.kts asks vard android-modules <app> and includes each library as :vard-<name>. Example: packages/firebase/native/android.

Versions and migrations

The gate compares the API with the previous published version:

ChangeMinimal step
a name, parameter, field or enum variant removedmajor
a type, bind, return value or the first (positional) parameter changedmajor
a parameter became required; a required parameter or a field without a default addedmajor
a name, enum variant, or a parameter/field with a default addedminor
nothing in the APIpatch

For 0.x a major change is a minor bump (0.3 → 0.4), as in Cargo.

error P015: API change since 1.0.0 is major: ! ~ view BarChart: `max` removed — the version must be at least 2.0.0
  fix: version = "2.0.0"

Accompany every rename with [[migrate]] — then vard check --fix rewrites the consumer’s code by itself. from = "X.y" means, depending on what X is in your package: a view’s parameter, an enum’s variant (.y in consumer code), or a struct’s field (both X(y: ...) and value.y).

Behavior is checked too

For a minor or patch release the gate also runs the previous version’s example/ tests against the new code. They are what consumers relied on; if they fail, the release changes behavior even when the API diff is clean (P023):

error P023: behavior changed: the tests of 1.0.0 fail against 1.0.1:
  FAIL example/tests/total.vtest
    > expect "Total: 60"
  fix: restore the old behavior, or publish it as 2.0.0

On a new major line the old tests only produce a warning.

Registries and hosting

A Vard registry is static files. Reading is plain GETs with no server logic; writing (publishing) happens in one place and always passes the same gate. So a registry can live anywhere — in a directory, in an S3/R2/GCS bucket behind a CDN, on GitHub Pages, on nginx — and be served through untrusted mirrors.

The public registry

vardemin/vard-registry is the default registry of vard (name vard, https://vardemin.github.io/vard-registry). It is this same format, kept in a GitHub repository and served by GitHub Pages — free for open source, no server to run:

  • Publishing is a pull request. Copy the package to submissions/<name>/ and open a PR; the check workflow runs vard publish --dry-run with the PR author as the owner. After a merge, the publish workflow publishes as the PR author, removes the submission, commits public/ and redeploys Pages.
  • The signing key lives only in the repository’s Actions secrets (and with the maintainer); its public half is compiled into vard, so even the first contact is verified — no trust-on-first-use window.
  • Ownership is the GitHub login of the first publisher; later versions must come from their pull requests.

The rest of this page describes the format and how to run a registry of your own.

The log and its signature

log.txt    1 charts 1.0.0 <archive sha256> <chain_1>
           2 charts 2.0.0 <archive sha256> <chain_2>
           chain_n = sha256(chain_{n-1} " " n " " name " " version " " sha)
log.head   2 <chain_2> <ed25519("vard-log/1 2 <chain_2>")>

On first contact with a registry the client:

  1. pins its key (~/.vard/known_registries, like SSH’s known_hosts); a changed key is P005;
  2. verifies the head’s signature and recomputes the chain;
  3. checks that the head it saw last time is a prefix of the new log (history was not rewritten) — P005;
  4. installs only an archive whose (name, version, sha256) is in the log and whose hash matches — P004.

vard registry verify DIR|URL verifies a whole registry: signatures, chain and every archive.

Rotating the key

vard registry rotate-key ./reg

The old key signs a rotation record {from, to, sig} that stays in config.json; the log head is re-signed with the new key, and the old secret is kept as private/registry.key.<id>.old. A client that trusts the old key (pinned, or compiled in for the public registry) follows the chain of signed rotations to the current key and re-pins it silently; a key that no signed rotation links to is still P005. After rotating, publish public/ and update the CI secret with the new private/registry.key.

The web page

Every registry gets public/index.html (written by vard registry init, added by the next publish to older registries): a single static page, no external scripts, that reads catalog.json and index/NAME.json. It shows search over names, keywords, summaries and exports; capabilities with sensitive ones highlighted; publish-time test results; versions with publication time, yank status and provenance; the generated API; and the vard add NAME command. vard registry serve serves it at /.

Private registries and mixing

A dependency comes from exactly one registry: its own registry = "..." or the default registry. A name from a private registry cannot be “hijacked” by a public one, and vice versa. For mirrors: a mirror needs no trust — it serves the same signed files.

Scaling

The current format targets thousands of packages: a client reads only the indexes of the packages it needs; the catalog is one file. For large registries (roadmap): a Merkle tree instead of the full log (O(log n) inclusion proofs, like Go’s sumdb), a sharded catalog, key rotation with the new key signed by the old one.

Over-the-air updates (OTA)

An interpreted bundle can be replaced without rebuilding and reinstalling the app — on one condition: the native part has not changed. That is exactly what the native fingerprint checks.

ChangeFingerprintDeliverable OTA
layout, logic, styles, textssameyes
a new version of a package without native codesameyes
a new extern fn / extern event or a new native moduledifferentno — needs a new app release
 
vard ota init ./channel                       # once: prints the channel key to compile into the app
vard ota publish examples/todo --channel ./channel --version 1.0.1

channel/
  public/config.json                    {"vard_ota": 1, "key": "<ed25519 public key>"}
  public/bundles/<sha256>.vpk           immutable bundles
  public/<native_fingerprint>/latest.json   {"sha256", "size", "version", "published", "sig"}
  private/ota.key                       the signing key — never publish it

latest.json is signed over vard-ota/1 <fingerprint> <sha256> <version>. A device:

  1. downloads <its own fingerprint>/latest.json and the bundle it names (static hosting, any CDN);
  2. calls vard_ota_install(latest, bundle, len, key, fingerprint, dir) (C ABI; Rust vard_ffi::ota_install) — it checks the signature with the key compiled into the app, the bundle hash, the fingerprint inside the bundle and that the sources compile, then writes the bundle to dir atomically; any failure leaves the current bundle in place;
  3. loads dir instead of the built-in bundle on the next start.

Implemented: channels, publishing, verification and installation (tested in crates/vard-ffi/tests/ota.rs). Not yet: the download-and-swap loop inside the Android and iOS shells (a few dozen lines of platform code around vard_ota_install).

The channel is addressed by the fingerprint, so a device physically cannot receive a bundle that needs native code it does not have. For AI-first development this closes the loop: an agent fixed a bug → the tests passed headless → a bundle with the same fingerprint safely goes to users; a change that needs new native code automatically becomes a store release.

Reproducibility

  • The same vard.toml gives the same version selection (MVS); vard.lock pins the hashes.
  • .vpk archives are deterministic: sorted paths, no timestamps, no permissions.
  • vard bundle gives the same sha256 for the same inputs on any machine.
  • Offline: packages from the cache (~/.vard/cache/), builtin and path dependencies need no network.

Package security model

The starting premise: dependencies are added by an agent that can make mistakes and can be deceived by text (documentation, an issue, a web page). So the system is built so that (1) the agent cannot install the wrong thing, (2) a package cannot get more than a person approved, and (3) nobody between the author and the device can substitute the code.

What the system does not promise

  • No malicious intent in a package’s code. Capabilities limit what a package can do, not how: a package with approved network can send data. The approval is a person’s decision; vard info shows why each capability is needed.
  • Native code. The native capability means running the package’s Kotlin/Swift code outside Vard’s limits. Approve it as carefully as a Gradle dependency.
  • Availability. A mirror can withhold updates (a freeze attack). That is detectable only by comparing with another source; log witnesses are on the roadmap.

Recommendations

  • Commit vard.lock and watch caps= and sha256= in diffs.
  • In CI: vard install (without --allow) fails if someone added a dependency with an unapproved capability; run vard registry verify URL periodically.
  • Keep a registry’s private/ out of public hosting; keep the key in CI secrets.
  • For agents: the vard-packages skill already contains the rule “on P008, stop and ask the user”.

vard-lang

  • Lexer — line breaks are separators (except inside (/[ and before continuation lines .x, &&, ?, :). It catches ;, ===, @State and the like right away, with a fix.
  • Parser — recursive descent, the AST in flat arenas (ExprId/UiId = u32), so the runtime keeps cheap indices in effects. Recovery at the line and declaration level: one run reports as many independent errors as possible; “unknown name” cascades after a syntax error are suppressed.
  • Checker — the expected type flows down: .center, .primary and lambda parameters are inferred without annotations. The Unknown type after an error is compatible with everything — no avalanche of secondary errors. When the fix is obvious (an alias or an edit distance), checking continues as if it were already applied — one iteration instead of several.
  • registry.rs — the single source of truth: elements, props and their types, enums, color tokens, the type scale, alias tables. vard doc is generated from it too.

Packages: linking, API, capabilities (vard-lang)

  • link.rs — namespaces without imports. Package files arrive with @name/... paths, the graph comes from vard.lock (or a LinkInfo from the CLI, with migrations). Resolution order: own → direct dependencies → std. Conflicting package declarations are renamed to pkg.Name before type checking, so the checker and the runtime work with unique names and know nothing about packages. Errors E0230–E0235; package migrations become E0234 with a fix, and checking continues as if it were applied.
  • api.rs — the public API (canonical items, a diff classified as major/minor/patch) and capabilities computed from the code with evidence (secureGet @ file:line).

vard-pkg

The data and protocol layer of the package manager, with no TLS stack: a TOML subset with diagnostics and fixes, semver, minimal version selection, vard.lock, deterministic .vpk, registries (builtin — the embedded packages/, a directory, HTTP) with key pinning and verification of the signed hash chain, and loading a project with its dependencies for the compiler (self-healing: a stale lock is reinstalled).

vard-runtime

  • Reactivity. state → Signal, let and view parameters → Computed (lazy, cached, auto-tracked), every dynamic prop → an Effect writing one field of one node; if/for → structural effects. Ownership is a tree of Scopes: disposing a scope frees everything created inside (effects, nodes, signals). Effects run in creation order (parent before child), which rules out glitches.
  • Equality cut-offs at every level: a signal does not notify for the same value, a prop does not touch the node for the same value, unchanged props do not mark layout dirty; static props (literals, enums, lambdas) create no effects at all.
  • Keyed for. Reconciliation by the by key; each row has its own value signal, so changing one item of a 3000-item list re-runs one row’s effects (measured: 7 actions over 3000 rows — 35 effect runs).
  • Values — Rc + copy-on-write (Rc::make_mut): copying is free, mutation never creates aliases. That makes the semantics predictable for a model.
  • Layout — constraints down, sizes up, one pass. CSS flex semantics (align, justify, grow, gap). Every node remembers why it got its size on each axis — why prints the chain. Line wrapping is cached by (font, width).
  • Inspection — the semantic tree (meaningless containers hidden, labels merged as in accessibility), diffs, selectors @id / #id / text, lints, state.
  • Runtime errors do not crash the app: any problem → an R diagnostic with file:line, the value becomes nil. Nodes from std views point at the place where the app uses the view.

The native bridge

  • The boundary is two declarations: extern fn (app → platform) and extern event (platform → app; on name(...) [if cond] { } handlers live while the view is on screen). Only data crosses (structs, enums, lists, maps, optionals) and callbacks fn(T) for results that come “later”; the checker forbids everything else (E0317).
  • The format is JSON. Encoding is untyped, decoding follows the type declared in Vard (struct fields by name, enums by variant name, defaults for missing fields). So one native function serves any app type: firestoreGet* in the firebase package returns a JSON document, and Vard turns it into a Profile or Note struct — whatever the developer declared.
  • Callbacks — functions in arguments become {"$callback": id}; the host answers with callback(id, json, keep). A closure created inside a handler pins the temporary scopes it captured — they outlive the call until the platform answers. A callback of a view that has already left the screen is dropped silently.
  • The std platform (std.vard): permissions, pref/prefGet, secure* (Keychain/Keystore), push and notifications, setColorScheme, openUrl, haptic, events appear/back/appResume/appPause/deepLink/push*, globals safeArea, keyboardHeight, backProgress, isDark, screenWidth.
  • Headless — Sim in the runtime plays the platform deterministically: real in-memory prefs/secure storage, the permission dialog answers what the test said, push/back/insets are injected by actions, restart models a cold start. User externs answer with a mock value or stay pending until resolve/send; packages’ [sim] sets defaults.
  • pref — state the runtime persists through the same boundary (prefGet/prefSet with the key vard.pref.<name>), one signal per name for the whole app.
  • Edge-to-edge and back — the host always draws under the system bars and passes the insets; safeArea adds them to padding. If the code never mentions safeArea, the runtime pads the root itself (a static flag from the checker). on back if cond tells the host whether the app intercepts back (a flag in the frame header) — that decides whether Android shows the system predictive animation or hands the gesture progress to the app.
  • Text on devices — the core measures the platform font through the host’s TextMeasurer (Android Paint.measureText), project fonts (fonts/) with the same file through fontdue. Line breaks and alignment on screen match what the layout computed.

vard-cli and MCP

Thin commands over the libraries. pkg.rs holds the package commands and the publish gate (shared by vard publish and the registry server); server.rs is the registry’s HTTP hosting. The MCP server (JSON-RPC over stdio) is stateless: vard_run mounts the app from scratch each time and replays the actions — 50–100 ms, deterministic, nothing to go stale between calls.

Roadmap

This version is a reference implementation of the core and tooling. For production on devices:

  1. Native shells. The Rust core builds as a cdylib/staticlib; Android — a Kotlin host (JNI), iOS — a Swift host (C ABI). The runtime emits a buffer of tree mutation commands (create/set/insert/remove), the host applies them per frame. Done: crates/vard-ffi (C ABI + JNI) and platforms/android (the :vard library with VardActivity, the :app shell, the firebase package’s native module). The host gets the whole frame — a flat list of draw records (format v2: shadows, gradients, per-corner radii, fonts, transforms, crates/vard-ffi/src/frame.rs); hit-testing and onTap bubbling stay in the core, Input is a native EditText over the Canvas; platforms/apple — the Swift package VardHost for iOS and macOS (VardView on a CAMetalLayer, VardViewController, the std modules over UserDefaults, Keychain, UserNotifications and the permission frameworks; include/vard.h is checked against the exported symbols). A mutation buffer instead of the full frame is the next step.
  2. Rendering. The main path is our own GPU renderer over the existing tree and layout: pixel-identical arbitrary designs and predictable performance. Native platform views are embedded where integration matters: text input with IME, maps, WebView, camera, video. Done: crates/vard-gpu — wgpu, one SDF pipeline (rounded boxes, borders, gradients, shadows, rounded clips), a glyph atlas from the core’s fonts, images; parity with the headless rasterizer is a test; the Apple host draws with it on Metal, native text fields float over Inputs (Rendering). Every host now draws with it: Android (SurfaceView, Vulkan/GLES, Canvas fallback), iOS/macOS (Metal), desktop (vard-desktop: winit + DX12/Vulkan/GL/Metal) and the web (vard-web: WebAssembly + WebGPU/WebGL2). Next: HarfBuzz-class shaping with system fonts.
  3. Execution. The AST interpreter is the dev engine (instant start, hot reload). For release — compilation to a compact register bytecode or AOT to Rust; type checks are already static, so runtime checks go away.
  4. Native modules. Done: extern fn with callbacks, extern event + on, the std platform (permissions, push, prefs, secure storage, back, insets), vard bindings --kotlin and --swift (the Swift output is type-checked by swiftc in CI), self-registering module libraries, Firebase as a package with a native module, automatic inclusion of packages’ native modules in the Android build. Next: async/await sugar over callbacks.
  5. Language. Done: Map, pref, Grid, wrap, shadows/gradients/fonts, localized text (strings tables, t(), the locale global — checked at compile time). Animations: animate: interpolates prop changes in the effect layer without re-running logic, enter: transitions, a frame clock from the host (vard_advance, the animating frame flag) and wait MS for deterministic tests. Next: navigation as a built-in element (today a stack + on back pattern), exit transitions, gestures, virtualized long lists, image caching.
  6. Accessibility. The semantic tree exists — mapping it to TalkBack/VoiceOver.
  7. On-device inspection. Done: the action protocol over TCP (vard run --device), a listener in vard-ffi that runs scripts on the UI thread, enabled in debuggable Android builds. Next: a device parameter for the MCP tools.
  8. Packages. Done: vard.toml/vard.lock, MVS, the namespace linker, API and capabilities from the compiler, enforced semver, migrations, the publish gate, a static signed registry, vard registry serve, vard bundle with the native fingerprint, git sources, enum/field migrations, behavioral checks with the previous version’s tests, quarantine and provenance, signed key rotation, a web page per registry, the public registry, signed OTA channels with on-device verification (vard ota). Next: the OTA download loop in the hosts, Merkle inclusion proofs, Sigstore attestations (see the package overview).

Rendering and animation

One draw list, three painters

After layout the core flattens the tree into a list of draw records in paint order — the frame format: rectangles in screen space with offset/scale applied, per-corner radii, borders, gradients, shadows, the clip (with the rounded clip of the innermost clip: true ancestor), opacity, text lines as the core wrapped them, inputs and images. Three painters draw that list:

The GPU renderer (crates/vard-gpu)

One WGSL pipeline draws instanced quads; every shape is a signed distance field evaluated per pixel:

  • rounded boxes with four radii — fills, borders (sdf ∈ [-width, 0]), side borders;
  • linear gradients — up to four evenly spaced stops along the CSS gradient line (longer lists are resampled);
  • soft shadows — the shape’s SDF smoothed over the blur radius, offset by shadowY;
  • clipping — every instance carries its clip rectangle and the rounded clip radii, so clip: true cards with radius cut their content without stencils;
  • text — glyphs rasterized by fontdue from the same faces the core measured with, packed into a 2048² coverage atlas (cleared when it fills up); synthetic italic shears rows like the rasterizer;
  • images — PNGs from the project folder as textures, cover/contain/fill, tint.

Instances that share an image are drawn in one call. Blending is premultiplied alpha in the sRGB-encoded space, like the rasterizer and the platform canvases, so colors match. crates/vard-gpu/tests/parity.rs renders a screen with every feature on the GPU and with tiny-skia and requires a mean channel difference under 1.5/255 (it is about 0.1).

Mobile and web hosts float native text fields over Inputs (IME, selection, autofill), so the renderer leaves Input text to them (Options::native_inputs). The desktop host edits text itself: the renderer then draws the text and a caret in the focused Input (Options::focused, Options::caret).

Text is drawn with the core’s fonts on every GPU host, and the core measures with the same fonts, so line breaks on a device match vard run. Project fonts (fonts/) are used when present, otherwise the bundled DejaVu.

Animation

animate: makes prop changes smooth without re-running logic: when an effect writes a new value to an animating element, the runtime keeps the current value on the node and records a tween to the new one. The clock is driven from outside:

  • devices call vard_advance(app, dt_ms) on each vsync while the frame header has the animating bit (Android: Choreographer, Apple: CADisplayLink), then draw;
  • tests and agents call wait MS, so screenshots and assertions mid-animation are deterministic.

Interpolated props: opacity offsetX offsetY scale radius border width height background color borderColor tint. Curves: .spring (damped, ζ = 0.75), .bouncy (ζ = 0.42), .easeOut, .easeInOut, .easeIn, .linear; duration: in ms. Interrupting a running animation starts the new one from the current value. enter: (.fade .slideUp .slideDown .slideLeft .slideRight .scale .pop) runs once when an element is first laid out.

  • Drawing: by default the GPU renderer (crates/vard-gpu) on a SurfaceView — Vulkan, GLES where Vulkan is missing — with text measured and drawn with the core’s fonts. ADR-0001: Our own Vard language instead of a DSL in Kotlin/Swift/TS

Status: accepted

Context. Applications are written by an LLM. It needs a short reference, unambiguous rules, instant checking with fixes, and clear errors. Existing languages offer a huge surface (generics, inheritance, async models, 1–5 minute toolchain builds) and compiler errors designed for people.

Decision. A small statically typed language with syntax close to Swift/Kotlin/TS (strong priors in models), one way to write each thing, and a compiler that knows models’ typical “habits” from other frameworks and turns them into machine fixes.

Consequences. + the full reference ≈ 3k tokens; a check ≈ 20 ms; errors fix themselves. − we maintain our own compiler and tooling; platform interop only through extern fn (see the roadmap).

ADR-0002: Fine-grained reactivity without a virtual DOM

Status: accepted

Context. Performance is a key criterion. The “re-render a component and diff the trees” model (React, Compose recomposition, SwiftUI body) spends work proportional to the size of the subtree and requires memoization from the author — something models systematically get wrong.

Decision. Signals/computed/effects (like Solid/Leptos): a view body runs once, every dynamic prop is a separate effect, structural if/for are effects over fragments, keyed lists have a value signal per row, and equality cut-offs apply at every level.

Consequences. + the cost of an update is proportional to the change, not to the UI size; the author needs no memo/key tricks (except by in lists, which the compiler checks). − state cannot be changed while the UI is being computed (R0003) — a deliberate restriction caught by the runtime.

ADR-0003: Text inspection as the primary debugging interface

Status: accepted

Context. A screenshot costs a model ~450–1600 tokens and requires “vision” to understand what is where. And exact sizes and the causes of a layout cannot be extracted from a picture.

Decision. A deterministic headless runtime and an action language (tree, tap, type, why, state, lint, expect). Mutating actions print a diff of the semantic tree. Tests (.vtest) and MCP use the same language. A bundled font makes layout identical on every machine.

Consequences. + a screen ≈ 100 tokens, an action ≈ 30; reproducible bugs and tests without an emulator. − the headless render is not pixel-identical to the platform; the final visual check happens on a device (plan: the same protocol over a WebSocket to the device).

ADR-0004: A knowledge base for agents, in English, compiled into the tool

Status: accepted (amended: all documentation is in English)

Context. Documentation a model reads must be short, precise and must not drift from the compiler’s behavior.

Decision. knowledge/llms.txt is the complete reference; it is compiled into the binary (vard doc, vard_doc in MCP), so the reference version always matches the compiler version. Element descriptions (vard doc Text) are generated from registry.rs. Texts for agents are in English (fewer tokens, stronger priors). The documentation for people — README and the docs/ site (https://vardemin.github.io/vardui/) — is in English too, so one language serves the whole community; it was originally written in Russian. vard new puts AGENTS.md, CLAUDE.md, skills and .mcp.json into every project.

Consequences. + one source of truth; an agent gets everything it needs with one command. − when the language changes, llms.txt and the skills must be updated; the snippets from the vard-app skill live in examples/patterns and are checked by vard test.

ADR-0005: Packages with a contract computed by the compiler

Status: accepted

Context. Dependencies in VardUI projects are added mostly by an LLM agent. In classic package managers (npm, Cargo, pub, SwiftPM) a package is described by its author’s claims: version, description, changelog. For an agent that means: (1) a guessed name may belong to someone else’s package (slopsquatting), (2) semver and descriptions cannot be verified more cheaply than by reading the code, (3) what the package does with the device is written down nowhere, (4) an upgrade requires reading a changelog and editing by hand. Separately: the language deliberately has no imports (ADR-0001), and packages bring in foreign names.

Decision.

  1. A package = code + a contract computed by the compiler (public API and capabilities) + knowledge (AGENT.md ≤ 6 KB, the generated API, skills) + proof (headless tests at publish)
    • migrations ([[migrate]] → E0234 with a fix:) + simulation ([sim]).
  2. Semver is enforced: the registry compares the API with the previous version (P015).
  3. Capabilities (secure permissions push native network prefs links share deeplinks) are computed from the code; the manifest must match (P013); a person approves sensitive ones in [policy] (P008); vard.lock records them.
  4. Installation by exact names only (P001 with “did you mean”); the registry cuts off look-alike names (P010).
  5. Namespaces without imports: own → direct dependencies → std; a conflict of two packages — pkg.Name; transitive dependencies are invisible; _ is private; native names are global. The linker renames conflicting declarations before type checking — the runtime knows nothing about packages.

Consequences. + an agent knows a package’s API and risks before installing, upgrades mechanically, cannot install a guessed name or grant a package unapproved rights; adding a package does not change the meaning of other code. − packages need an AGENT.md and an example with tests; one version of a package per app (a consequence of the shared namespace); capabilities limit “what”, not “how” (an approved network can still send data).

ADR-0006: Minimal version selection instead of a solver

Status: accepted

Context. Dependency solvers (npm, Cargo, pub, pip) pick the “newest compatible” version. The result depends on when they run; reproducibility comes from a lockfile, and losing or regenerating it changes behavior. Solver errors (“could not find a consistent set”) are hard to explain and fix — especially for a model. On top of that, a Vard app links one version of each package (a shared namespace), so version selection must be unambiguous.

Decision. Minimal version selection (as in Go modules). A requirement is a minimum on a compatibility line ("1.4" = ≥ 1.4.0, < 2.0.0; 0.x lines are separate). Walk the requirement graph from the app; for each package take the largest of the minimums; requirements on different lines are P006, listing who wants what. Versions on a line are published only in increasing order, so “the smallest existing version ≥ the minimum” is stable. An upgrade is an explicit edit of the requirements in vard.toml (vard update), visible in the diff.

Consequences. + the same result today, tomorrow and in CI, with or without a lockfile; no backtracking; every error is explainable in one line; the lockfile only pins hashes and capabilities. − new fixes do not arrive by themselves — vard update brings them; package authors should raise their minimum requirements when they need a dependency’s fix.

ADR-0007: A static, content-addressed registry with a signed log

Status: accepted

Context. A registry must be cheap to host (for a team, a company, a community), work behind any CDN and through mirrors, and trust in packages must not depend on who serves them. Server-side read logic (search, version resolution) complicates mirroring and scaling.

Decision.

  1. The read protocol is static files: config.json, catalog.json (the client searches), index/NAME.json (JSON lines, append-only), blobs/SHA256.vpk (immutable, cached forever).
  2. The .vpk archive is deterministic (sorted paths, no metadata), so the hash is reproducible.
  3. The publication log is a hash chain log.txt whose head is signed with ed25519 (log.head). A client pins the key on first contact and checks the signature, the chain, that the previously seen head is a prefix, and that every installed version is in the log.
  4. Writes happen in one place and through one gate: vard publish --registry DIR, CI over a git repository holding the registry, or vard registry serve (an HTTP publish API with tokens).
  5. HTTPS goes through the system curl, so the binary carries no TLS stack; integrity does not depend on the transport.

Consequences. + a registry is a directory served by anything; mirrors need no trust; substitution of an archive, the index or the history is detected by the client; one gate for every publishing path. − the client downloads the full log (for large registries, Merkle trees and inclusion proofs are on the roadmap); a mirror withholding updates is detectable only by comparing with another source.
